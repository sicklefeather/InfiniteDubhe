# 游戏引擎需求文档

> 文档版本：M2
> 更新日期：2026-08-15
> 状态：M0 / M1 / M2 已完成（见 §12）

---

## 1. 文档说明

### 1.1 目的
本文档定义 C# 游戏引擎 **无限天枢引擎（Infinite Dubhe Engine）** 的需求，作为后续架构设计（`设计文档.md`）、任务拆解与迭代开发的依据。文档描述"引擎要做什么、做到什么程度、以什么顺序做"，不涉及具体代码实现。

### 1.2 读者
- 引擎开发者（本人）
- 未来可能的协作者

### 1.3 术语
| 术语 | 说明 |
|------|------|
| 引擎（Engine） | 本文档描述的游戏引擎本体 |
| 宿主应用（Host） | 使用引擎的游戏/应用项目 |
| 场景（Scene） | 运行时对象的容器，承载一组实体与逻辑 |
| 实体（Entity） | 游戏世界中的最小逻辑单位 |
| 组件（Component） | 挂在实体上的一段可复用数据+行为 |
| 资源（Asset） | 纹理、音频、字体、场景、材质等可被加载的内容 |
| 平台抽象层（PAL） | 屏蔽不同平台差异的接口层 |
| 渲染后端 | 实际调用图形 API（DX11/12、Vulkan、GL）的实现 |

## 2. 项目背景与目标

### 2.1 背景
- 语言：C#（.NET）
- 定位：自研通用游戏引擎
- 当前阶段：**仅 2D 游戏**
- 未来阶段：3D、多平台

### 2.2 总体目标
1. 提供一个**从零可掌控**的 C# 游戏引擎，而非基于 Unity/Godot 的二次封装。
2. **当前**：稳定支撑 2D 游戏的完整开发闭环（渲染、物理、输入、音频、资源、UI）。
3. **未来**：架构上为 3D 渲染管线、跨平台预留扩展点，避免推倒重来。
4. 借鉴 Unity / UE / Godot / Cocos 的成熟设计理念，但**保持实现简单、可维护、可测试**。

### 2.3 非目标（本期不做）
- 不追求与商业引擎（Unity/UE）功能对等。
- 不内置完整的可视化编辑器（后续作为独立工具规划，见 §13）。
- 不实现自有物理引擎（复用第三方开源库）。
- 不做 3D 渲染（仅保留架构预留）。

## 4. 技术选型建议（待定项）

> 本节为**建议**，需在架构设计阶段最终确认。核心原则：**少造轮子、跨平台、.NET 生态**。

### 4.1 推荐方案

| 领域 | 建议 | 理由 / 备选 |
|------|------|------------|
| 运行时 | .NET 10（LTS） | 性能与生态；`net10.0` 起步 |
| 图形/窗口基础 | **Silk.NET** | 跨平台（DX11/12、Vulkan、OpenGL、Metal），官方维护，AOT 友好 |
| 2D 渲染 | 自研 Sprite 批处理（基于 Silk.NET） | 引擎核心价值；备选：直接用 MonoGame |
| 数学库 | **System.Numerics** 或自定义 `Mathf` | 统一 float/double；备选：Silk.NET.Maths |
| 2D 物理 | **Aether.Physics2D 2.2.0**（Box2D 的 C# 移植） | `net8.0`，net10 可直接引用；Farseer 系、纯托管、无第三方依赖；封装层做 `System.Numerics` 数学类型适配；备选：VelcroPhysics |
| 3D 物理（预留） | **BepuPhysics v2** | 高性能、纯 C#、MIT |
| 音频 | 跨平台绑定（OpenAL / Silk.NET 音频） | 备选：NAudio（仅 Windows） |
| 图像解码 | **StbImageSharp** | 轻量、跨平台、公共领域（Public Domain） |
| 字体/文字 | StbTrueTypeSharp 或 自研位图字体 | 2D 阶段用位图字体即可 |
| 序列化 | **System.Text.Json**（已确定） | 场景/资源配置；先 JSON（可读、调试友好），后续性能不足再评估二进制 |
| 测试 | xUnit / NUnit | 单元测试 |
| 日志 | Microsoft.Extensions.Logging | 标准、可替换 |

### 4.2 关键决策状态

**已确定 ✅**
1. **图形/窗口基础**：基于 **Silk.NET** 自研，不基于 MonoGame。自主可控，符合"自研引擎"定位。
2. **序列化格式**：**JSON**（System.Text.Json）。
3. **实体系统模型**：**GameObject-Component**（Unity 式），见 §6.2。
4. **小程序平台**：**暂不考虑**，后续另行评估。
5. **脚本/逻辑层边界**：引擎与游戏逻辑**分属不同程序集（静态引用）**，不做运行时插件式热加载；逻辑热重载暂不实现，先做资源热重载。
6. **2D→3D 抽象策略**：接口克制、按需抽象，不预先设计 3D（见 §13 Q6）。
7. **音频后端**：**OpenAL**（Silk.NET.OpenAL），原生库 **OpenAL Soft**（`soft_oal.dll`）经 `Silk.NET.OpenAL.Soft.Native` 打包进输出目录，未安装 OpenAL 的机器也能出声。

> 唯一遗留的风险项见 §13 Q7（单人维护的工作量控制）。

## 5. 平台需求

### 5.1 本期目标平台
- **Windows 10/11（x64）**：唯一必须支持的平台。

### 5.2 未来平台（仅预留，不实现）
| 平台 | 优先级 | 备注 |
|------|--------|------|
| Android | P3 | 需 IL2CPP/NativeAOT 或 Mono 运行时 |
| Web（WASM） | P3 | 需 WebGL/WASM 后端 |
| Linux / macOS | P3 | Silk.NET 天然支持，成本较低 |

### 5.3 平台抽象层（PAL）需求
无论当前是否多平台，引擎代码必须通过 **PAL 接口** 访问平台相关能力，禁止在核心逻辑中直接调用平台 API：
- 窗口创建与管理
- 图形上下文创建（含交换链）
- 输入（键盘/鼠标/触摸/手柄）
- 文件系统与路径
- 定时器/时钟
- 音频设备

**验收标准**：Windows 实现之外，抽象接口本身不包含任何 Windows 专属类型。

## 6. 核心架构需求

### 6.1 分层架构（自顶向下）
```
┌─────────────────────────────────────┐
│        游戏 / 宿主应用（Host）        │
├─────────────────────────────────────┤
│        引擎上层（Engine API）         │
│  场景管理、实体系统、组件、渲染入口    │
├─────────────────────────────────────┤
│   引擎子系统（独立模块，可替换）       │
│  渲染器 │ 物理 │ 音频 │ 输入 │ 资源  │
├─────────────────────────────────────┤
│    平台抽象层（PAL，跨平台接口）       │
├─────────────────────────────────────┤
│    第三方库（Silk.NET / 物理 / 图像）  │
└─────────────────────────────────────┘
```

> 各程序集之间的具体依赖方向（谁可引用谁）以 `设计文档.md` §3.1 为准。

### 6.2 实体系统模型（已确定）
**采用：GameObject-Component 模型（类似 Unity/Godot Node）**，理由：
- 2D 游戏开发直观、调试友好、门槛低。
- 未来若性能不足，可**增量引入 ECS 用于特定高频子系统**（如渲染、粒子），两者不冲突。

**需求要点**：
- 实体由"标识符 + 组件列表"组成，实体本身无逻辑。
- 组件为纯数据 + 可选行为（Update/事件回调）。
- 支持组件增删、查找（按类型/标签）、父子层级变换（Transform 层级）。
- 实体/组件的生命周期管理明确（创建、启用/禁用、销毁）。

### 6.3 主循环（Game Loop）
- 固定时间步（Fixed Update）+ 可变渲染帧（Render）分离。
- 支持逻辑与渲染解耦，未来可做确定性模拟（存档回放）。
- 循环需支持暂停、步进（单帧）调试。

### 6.4 序列化与持久化约定（已确定）
- **统一门面**：引擎内部序列化一律通过自研 `ISerializer` 接口访问，不在业务代码中直接引用具体 JSON 库；该接口位于 `Core`，具体实现与 `JsonConverter` 位于 `Resources`。
- **底层实现**：采用 **System.Text.Json**（.NET 内置，零第三方依赖、AOT 友好）。
- **对用户透明**：用户调用高层 API（如 `LoadScene`），不直接接触 JSON 库；用户项目可自由使用任意第三方序列化库（如 Newtonsoft.Json），与引擎互不冲突。
- **需特殊处理**：场景/资源序列化中的对象引用（ID 引用）、多态（组件子类）、资源引用（纹理/音频 ID），通过自定义 `JsonConverter` 解决（详见 `设计文档.md`）。
- **引用重连与场景加载**：GUID / 多态 / 资源路径三类引用在反序列化阶段重连；从文件加载场景由 `Resources` 的 `SceneLoader` 负责（反序列化 + 引用重连），`SceneManager` 只做场景切换（详见 `设计文档.md` §4.3/§4.7）。

## 9. 非功能需求（NFR）

### 9.1 性能
| 编号 | 需求 |
|------|------|
| NFR-01 | 2D 场景下，1000 个精灵目标稳定 60 FPS（现代中端 Windows 硬件） |
| NFR-02 | 渲染层支持批处理，减少 Draw Call（目标：同类纹理合并） |
| NFR-03 | 帧内不产生非必要 GC 压力（关键路径避免装箱、减少分配） |
| NFR-04 | 启动时间目标：冷启动到首帧 ≤ 2 秒（不含资源加载） |

### 9.2 可扩展性 / 可维护性
| 编号 | 需求 |
|------|------|
| NFR-05 | 子系统之间低耦合，物理/音频/输入等模块可替换 |
| NFR-06 | 核心逻辑不依赖平台，平台能力全部经 PAL |
| NFR-07 | 渲染接口保持克制，不写死 2D 专用假设，为未来 3D 留出替换空间（但不预先设计 3D 抽象，见 §13 Q6） |
| NFR-08 | 公开 API 有文档注释，核心路径有单元测试 |

### 9.3 可测试性
| 编号 | 需求 |
|------|------|
| NFR-09 | 逻辑与渲染分离，游戏逻辑可在无图形环境下单测 |
| NFR-10 | 关键子系统（数学、场景、资源、物理封装）有测试覆盖 |
| NFR-11 | 支持无头（Headless）运行，用于自动化测试与 CI |

### 9.4 工程与交付
| 编号 | 需求 |
|------|------|

## 10. 模块依赖关系（概览）

> 权威的依赖方向见 `设计文档.md` §3.1，此处为概览。`Core` 同时承载跨层共享的契约类型（`ISerializer` 接口、渲染契约 `Color`/`ITexture`/`IRenderable` 等），避免 `Scene` 与 `Rendering` 反向依赖。

```
Engine.Core（基础：数学、容器、日志、时间、事件、序列化接口、渲染契约）
   ├── Engine.Platform（PAL 抽象，依赖 Core）
   ├── Engine.Scene（实体/组件/场景，依赖 Core）
   ├── Engine.Rendering（2D 渲染，依赖 Core + Platform）
   ├── Engine.Input（依赖 Core + Platform）
   ├── Engine.Audio（依赖 Core + Platform）
   ├── Engine.Resources（依赖 Core + Platform + Scene + Rendering；场景/纹理是资源类型）
   ├── Engine.Physics（封装第三方物理，依赖 Scene）
   └── Engine.UI（依赖 Rendering + Input + Scene）
```

---

## 11. 验收标准（MVP：M0 + M1）

引擎达到以下标准视为完成 MVP：
1. 在 Windows 上可启动一个窗口并稳定渲染。
2. 能加载一张纹理并以精灵方式显示、移动、旋转、缩放。
3. 能用键盘/鼠标输入驱动精灵移动。
4. 能创建场景、实体与组件，并触发生命周期回调。
5. 具备日志、事件系统与基础时间管理。
6. 提供一个可运行的示例 Demo（如：移动角色 + 碰撞一个静态方块）。
